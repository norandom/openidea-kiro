# Roadmap

## Overview

Version 2 of spec constraint checking, continued in this project: requirements whose words resolve to a declared, topic-scoped vocabulary, EARS-shaped acceptance criteria, and contradiction search that only compares requirements that talk about the same topic. Version 1 lived in `spec-kit-ears-tdd` (`ears-sdd` crate, Spec Kit layout), which is **retired**: this project is its successor. v1 taught two lessons that shape v2: term references matched textually across unrelated topics, and the Spec Kit parsing it relied on is not a reliable base. v2 targets the cc-sdd / kiro layout used here, with parsers written fresh against this repo's templates; the retired repo stays available read-only as prior art and as a source of regression cases.

The checking engine (`kiro-core`) is a pure Rust crate with two frontends: an OpenIDEA plugin (`plugins/kiro/`, sandboxed WASM component `openidea:plugin@0.1.0`, installed into `../openidea` as a dev plugin) that also adds spec ↔ code navigation and Mermaid/text visualization inside the IDE, and a CLI (`crates/kiro-cli`) that runs the same checks as a CI gate. The plugin sandbox has **no directory listing, no file writing, no open-file, no network** — everything enters via `host::read_file` / `active_file` and leaves via notifications, editor insertion, and command messages; the core crate therefore never touches the filesystem.

## Approach Decision

- **Chosen**: one pure, `std`-only core crate (`crates/kiro-core`: cc-sdd parsers, spec model, vocabulary, checks, renderers) consumed by two thin frontends — the wasm plugin and a native CLI. Vocabulary is a committed project file (`.kiro/vocabulary.toml`, seeded from an NVIDIA Auto Ontology export) whose terms carry a **topic**; specs declare their topics; term resolution and contradiction search never cross topics.
- **Why**: the plugin host API is the only IDE surface and forbids fs/network, so the engine must take strings anyway — which is exactly what a CLI can also feed it. Topic scoping is the fix for v1's cross-topic matching. Fresh parsers against this repo's cc-sdd templates avoid inheriting v1's Spec Kit parsing problems; `ears-sdd` remains prior art for edge cases (EARS false-positive fixes, BDD encoding choices), not a dependency.
- **Rejected alternatives**:
  - Path-depend on or vendor `ears-sdd` — no feature flags; pulls `clap`, `ignore`, `tempfile`, `biodivine-lib-bdd` and `std::fs` into the wasm build; its parsers target Spec Kit tables, not cc-sdd.
  - Host-side feature inside OpenIDEA core — user asked for a plugin; keeps the IDE core untouched.
  - Plugin shells out to a binary or calls Auto Ontology MCP at runtime — sandbox forbids processes and network.
  - Plugin-only engine — loses the CI gate that made v1 useful.

## Scope

- **In**: `kiro-core` (cc-sdd v3 parsers, spec/task/design/roadmap model, current-spec resolution, finding model, Mermaid/text renderers); `plugins/kiro/` package (manifest, WIT bindings, host wrapper, dispatch); navigation commands; visualization commands; topic-scoped vocabulary + term lookup; spec constraint checks (EARS shape, declared-before-use, topic mismatch, contradiction search); `kiro-cli` gate with text/JSON reports and exit codes; fixtures and unit tests; dev-plugin and CI usage docs.
- **Out**: changes to the OpenIDEA host (WIT, IDE core); running agents or implementing tasks (stays with the agent harness, e.g. OpenCode + cc-sdd); writing/editing spec or vocabulary files from the IDE; deploying or calling Auto Ontology services; Spec Kit (`.specify`) layout support (retired with v1).
- **Deferred to later waves (v1 features carried forward, not dropped)**: intentions and precedence between requirements; supersession/amendment envelope comparison (`contain.rs`); production-code separation (`separation.rs`); requirement → test traceability; `doctor`-style environment checks; vocabulary-backed component labels for navigation/visualization (a `Labeler` over `kiro_core::vocab::resolve`, living in the frontends); the "unreciprocated supersession" prose check (cross-spec). Each becomes a spec after the first wave ships; they all build on kiro-core + spec-constraints.

## Constraints

- Sandbox: no `read_dir`, no file writes, no open-file, no network, no env; per-call limits ~5·10⁹ fuel, 5 s, 256 MiB; a trap/panic marks the plugin Failed for the session, so command paths must not panic. `kiro-core` must compile for both `wasm32-wasip2` and native.
- Spec discovery without directory listing (plugin): feature names come from `.kiro/steering/roadmap.md` (`## Specs (dependency order)` list, lines `- [ ] name -- desc. Dependencies: a, b`), the active file's path under `.kiro/specs/<feature>/`, and command args. The CLI may walk `.kiro/specs` with `std::fs`. There is no project-level `.kiro/brief.md`; briefs live at `.kiro/specs/<feature>/brief.md`.
- Plugin API `openidea-api = "0.1"`; component builds with `wit-bindgen` to `wasm32-wasip2` (`opt-level = "s"`, `lto`, `panic = "abort"`); `plugins/kiro/Cargo.toml` carries its own `[workspace]` and depends on `kiro-core` by path.
- cc-sdd v3 layout compatibility: `.kiro/specs/<feature>/{spec.json, requirements.md, design.md, tasks.md}`. `spec.json.phase` ∈ `initialized | requirements-generated | design-generated | tasks-generated` (+ `approvals`); requirements are `### Requirement N` headings with `#### Acceptance Criteria` numbered `M.` (criterion id `N.M`); tasks are `- [ ] N.M (P)` items with `_Requirements: N.M_`, `_Depends: N.M_`, `_Boundary: <design component names>_`; `design.md` carries a File Structure Plan mapping components to files, and Mermaid blocks. `_Boundary:_` names design **components**, not files — file ownership is derived via the File Structure Plan.
- Vocabulary: `.kiro/vocabulary.toml` (TOML-first; imports only in the CLI — Auto Ontology's JSON term export as the primary input, since it exports no SKOS; SKOS Turtle as a secondary input). Every term has a `topic`; a spec declares its topics in `spec.json`; an undeclared topic means "no term checks", never a cross-topic match.
- Command `arg` delivery from the IDE UI is unverified (only `crates/ide-plugin/tests/host.rs` passes one) — plugin-core design must confirm it or provide a fallback.

## Boundary Strategy

- **Why this split**: the engine is the product; both frontends are adapters. Putting parsers, model, vocabulary, checks and renderers in `kiro-core` lets the plugin, the CLI and the tests share one truth, and lets navigation/visualization/constraint specs be designed and reviewed independently against a stable Rust API instead of against the sandbox.
- **Shared seams to watch**: the `Source` abstraction (string reads by project-relative path) is the only I/O seam — core never reads disk, frontends never parse markdown; file ↔ component ↔ task joining (File Structure Plan + `_Boundary:_`) is owned by core and used by both navigation and visualization; topic scoping is owned by vocabulary-grounding and must be honoured by spec-constraints, navigation labels and visualization labels; findings have one shape (`feature, severity, code, file, line, message`) rendered by both frontends.

## Specs (dependency order)

- [x] kiro-core -- pure crate: cc-sdd parsers (spec.json, requirements, tasks, design File Structure Plan, roadmap), spec model, file↔component↔task join, current-spec resolution, finding model, Mermaid/text renderers. Dependencies: none
- [x] plugin-core -- OpenIDEA plugin package: manifest, WIT bindings, host wrapper, `Source` over `read-file`, command dispatch, dev-plugin install. Dependencies: kiro-core
- [x] vocabulary-grounding -- topic-scoped vocabulary file (`.kiro/vocabulary.toml`) seeded from an Auto Ontology export, term resolution scoped by spec topics, `vocab.*` plugin commands. Dependencies: kiro-core, plugin-core
- [x] spec-navigation -- `nav.*` commands moving between requirements/design/tasks and the code they cover, in both directions, via the File Structure Plan join. Dependencies: plugin-core
- [ ] spec-visualization -- `viz.*` Mermaid/text renderings of the spec graph (phases, requirements → criteria → tasks → components → files, task dependencies). Dependencies: plugin-core
- [ ] spec-constraints -- v2 constraint checks: EARS shape, declared-before-use terms, topic mismatch, bounded contradiction search; `check.*` plugin commands. Dependencies: vocabulary-grounding
- [ ] cli-gate -- `kiro-cli` native binary running the same checks over a `.kiro` tree with text/JSON reports, exit codes, CI example, and vocabulary import (Auto Ontology JSON primary, SKOS Turtle secondary → TOML). Dependencies: spec-constraints, spec-visualization
