# Requirements Document

## Introduction

spec-constraints is the reason this project exists: specs are checked, not just written. Version 1 (`ears-sdd`, retired) checked EARS shape, declared terms and contradictions on the Spec Kit layout, and failed in one specific way — term references were matched textually across unrelated topics, so the contradiction search compared requirements that were never about the same thing and the gate lost trust. Version 2 re-implements the three checks on the cc-sdd layout, on top of the topic-scoped vocabulary that vocabulary-grounding provides, with a contradiction search that refuses rather than guesses.

This spec delivers the engine capability `kiro_core::checks` — the EARS shape check over every acceptance criterion, the declared-before-use term check over `_Terms:_` annotations resolved only inside the spec's declared topics, the annotation conventions `_Terms:_`, `_Guard:_`, `_Effect:_`, `_Conflicts:_` with a small refusable guard language, and a bounded, deterministic contradiction search with witness states — plus the four `check.*` plugin commands that surface the findings inside OpenIDEA, fixtures with known-good, known-bad and refused cases, and the documentation of the annotation conventions. The CLI gate that runs the same checks in CI is cli-gate; the vocabulary itself is vocabulary-grounding; the spec model and finding shape are kiro-core.

## Boundary Context

- **In scope**: the check entry point and its configuration (check selection, severity overrides, informational report switches, size caps); the EARS shape check with its masking rules and pattern classification; the declared-before-use term check and term suggestions; the parsing and validation of the `_Terms:_`, `_Guard:_`, `_Effect:_` and `_Conflicts:_` annotation values; the contradiction search, its witness and its refusal; the finding codes of this spec and their default severities; the `check.spec`, `check.ears`, `check.terms` and `check.contradictions` plugin commands and their degradation; fixtures and tests; the documentation of the annotation conventions and the proposed requirements-template change.
- **Out of scope**: loading, validating or resolving the vocabulary (vocabulary-grounding; this spec only calls its scoped resolution); capturing `_Key: value_` lines from `requirements.md` (kiro-core already records them generically on requirements and criteria); CLI reporting, exit codes and tree walking (cli-gate); v1's intentions and precedence between requirements, supersession envelopes, production-code separation and requirement → test traceability (later specs); comparing requirements across different specs; editing or auto-fixing spec files; applying the template change to the cc-sdd templates or skills; any change to the OpenIDEA host.
- **Adjacent expectations**: kiro-core supplies the feature model with criteria `N.M` (text with continuation lines joined, line spans, annotations on requirements and criteria), the finding shape, its catalogue and ordering, and the text renderers; vocabulary-grounding supplies the vocabulary status, the spec's declared topics, the scoped resolution with its five outcomes and term kinds (`entity`, `bool`, `enum`, `int`); plugin-core supplies command dispatch, spec resolution, argument parsing, per-spec variants and presentation, and delivers no argument from the IDE's own UI; cli-gate runs the check entry point of this spec over every feature of a tree and maps severities to exit codes; existing specs without annotations are expected to keep passing the term and contradiction checks.

## Requirements

### Requirement 1: Check Orchestration and Configuration
**Objective:** As a frontend author (plugin, CLI), I want one entry point that runs the constraint checks over a feature under a configuration and returns findings in the shared shape, so that the IDE and CI produce identical results.

#### Acceptance Criteria
1. The kiro-core engine shall provide one check operation that takes a loaded feature, the loaded vocabulary and a check configuration, and returns a check report containing the findings of the EARS, term and contradiction checks together with a record per check stating whether it ran, how many findings it produced, or why it was skipped.
2. The kiro-core engine shall provide a second form of the same operation that takes a workspace, a feature name and a configuration, loads the feature and the vocabulary through the workspace, and returns the same check report.
3. The check configuration shall allow selecting any subset of the three checks, overriding the default severity of any finding code of this spec, enabling or disabling the informational pattern reports of Requirement 2 and the term suggestions of Requirement 3, and setting the variable cap and node cap of Requirement 5, and the kiro-core engine shall supply a default value for every setting.
4. The kiro-core engine shall carry every check finding with the feature name, the project-relative path of the feature's requirements document and the 1-based line of the criterion or annotation concerned, sorted in the shared finding order, so that both frontends present them in the shared `path:line: SEVERITY CODE message` form.
5. If a feature has no readable requirements document, the kiro-core engine shall run no check for it and shall report every check as skipped with that reason, producing no check finding.
6. While a requirements document carries no `_Terms:_`, `_Guard:_`, `_Effect:_` or `_Conflicts:_` annotation, the kiro-core engine shall produce no finding of severity `warning` or `error` about that document from the term and contradiction checks (vocabulary-grounding's findings about `spec.json` and the vocabulary file are passed through unchanged), so that specs written before these conventions keep passing.
7. When a check is disabled by the configuration, the kiro-core engine shall report it as skipped and shall produce none of its findings.
8. Whenever the term or the contradiction check ran for a feature, the kiro-core engine shall record `CHECK_COVERAGE` of severity `info` on the requirements document, stating the number of criteria, the number of requirements and criteria carrying any of the `_Terms:_`, `_Guard:_`, `_Effect:_` or `_Conflicts:_` annotations, the number of pairs considered, the number of contradictions found and the number of refused pairs, so that a document without annotations is visibly reported as unchecked rather than passing silently.

### Requirement 2: EARS Shape Check
**Objective:** As a spec author, I want every acceptance criterion checked for EARS shape with the false positives of version 1 fixed, so that the gate rejects malformed criteria and only those.

#### Acceptance Criteria
1. The kiro-core engine shall check every criterion of every baseline and amendment requirement of the feature's requirements document, using the criterion text with its continuation lines joined.
2. Before applying the EARS rules, the kiro-core engine shall mask the content of balanced quoted literals delimited by straight or typographic double quotes, backticks, or single quotes that are not inside a word, shall leave an unbalanced quote unmasked, and shall treat an apostrophe between two word characters as part of the word, so that words inside literals and possessives never count as modals or structure.
3. If the masked text contains no `shall` as a whole word, the kiro-core engine shall record `EARS_NO_SHALL` of severity `error` at the criterion line.
4. If the masked text contains two or more occurrences of `shall` as a whole word, the kiro-core engine shall record `EARS_MULTI_SHALL` of severity `warning` at the criterion line naming the count.
5. If the masked text contains `should`, `must`, `may` or `will` as a whole word that is not joined to a neighbouring word by a hyphen, the kiro-core engine shall record `EARS_MODAL` of severity `warning` at the criterion line naming the modal found.
6. When the criterion begins with `When`, `While`, `Where` or `If` followed by a space (case-insensitive), the kiro-core engine shall take the condition clause as the text up to the last comma before the first `shall` and, if no such comma exists, shall record `EARS_NO_TRIGGER` of severity `warning` at the criterion line.
7. When the criterion begins with `If`, the kiro-core engine shall accept both `If …, then the [system] shall …` and `If …, the [system] shall …` as the unwanted-behaviour pattern.
8. If exactly one `shall` is present but the subject between the condition clause and the `shall` is empty, or the response after the `shall` is empty, the kiro-core engine shall record `EARS_UNPARSED` of severity `warning` at the criterion line stating which part is missing.
9. The kiro-core engine shall classify every criterion with exactly one `shall` as ubiquitous, event-driven (`When`), state-driven (`While`), unwanted-behaviour (`If`), optional-feature (`Where`) or complex (two or more condition keywords at clause starts before the `shall`), and, while pattern reports are enabled, shall record `EARS_PATTERN` of severity `info` at the criterion line naming the pattern.
10. The kiro-core engine shall report no EARS finding for a criterion that contains a modal only inside a quoted literal, a modal only as part of a hyphenated compound, or a possessive apostrophe, and shall not let a comma inside the response change the trigger decision, so that the false positives found in version 1 stay fixed.

### Requirement 3: Declared Terms
**Objective:** As a spec author, I want to declare the terms a requirement is about and have them resolved only inside my spec's declared topics, so that a word that exists in another topic is reported as a mismatch instead of silently matched.

#### Acceptance Criteria
1. The kiro-core engine shall read the `_Terms:_` annotation of a requirement block as a comma-separated list of declared terms (trimmed, empty entries dropped, duplicates after label normalisation dropped), and shall read a `_Terms:_` annotation on a criterion as terms declared for that criterion in addition to its requirement's terms.
2. While the spec declares topics and the vocabulary is loaded, the kiro-core engine shall resolve every declared term through the scoped resolution of vocabulary-grounding with exactly the spec's declared topics, and shall offer no check that resolves a term without them.
3. When a declared term resolves as found, the kiro-core engine shall record no finding for it, and when the found term is deprecated the kiro-core engine shall record `TERM_DEPRECATED` of severity `warning` at the annotation line naming the replacement when one exists in the declared topics.
4. If a declared term resolves as not in topic, the kiro-core engine shall record `TERM_TOPIC_MISMATCH` of severity `error` at the annotation line naming the topics and ids where the term exists and the spec's declared topics, and shall never treat the term as resolved.
5. If a declared term resolves as unknown, the kiro-core engine shall record `TERM_UNDECLARED` of severity `error` at the annotation line naming the term and the declared topics.
6. If a declared term resolves as ambiguous, the kiro-core engine shall record `TERM_AMBIGUOUS` of severity `warning` at the annotation line naming the candidates and asking for the term id.
7. While term suggestions are enabled, if a label or alternative label of a term visible to the spec occurs as a whole-word phrase in a criterion's masked text while that term is declared neither on the requirement nor on the criterion, the kiro-core engine shall record `TERM_SUGGESTED` of severity `info` once per requirement and term at the requirement heading line, naming the label and the criteria in which it occurs.
8. While the spec declares no topics or the vocabulary is missing or invalid, the kiro-core engine shall perform no term resolution, shall include the corresponding vocabulary-grounding finding (`TOPICS_UNDECLARED`, `VOCAB_MISSING` or `VOCAB_INVALID`) once in the report, and, if the requirements document carries any `_Terms:_`, `_Guard:_`, `_Effect:_` or `_Conflicts:_` annotation, shall record `CHECK_UNSCOPED` of severity `warning` at the first such annotation line stating that the annotations cannot be checked and why.
9. If a declared topic is unknown to the vocabulary, the kiro-core engine shall include vocabulary-grounding's `TOPIC_UNKNOWN` finding once in the report and shall continue with the remaining declared topics.

### Requirement 4: Guard, Effect and Conflict Annotations
**Objective:** As a spec author, I want to state when a criterion applies and what it requires in a small language that refuses what it does not understand, so that the contradiction search works on meaning and never on a misreading.

#### Acceptance Criteria
1. The kiro-core engine shall read a `_Guard:_` annotation on a criterion as its applicability condition, written in a grammar consisting of `or`-separated conjunctions, `and`-separated negations, `not`, parentheses, a bare term reference (the boolean term holds), and comparisons `term op literal` with `op` one of `=`, `==`, `!=`, `<`, `<=`, `>`, `>=` and a literal that is an integer, `true`, `false`, a quoted word or a bare word.
2. The kiro-core engine shall match a term reference in a guard or effect against the terms declared on the criterion's requirement or on the criterion, comparing the reference with each declared term's resolved id and with the declared name as written with internal whitespace replaced by hyphens, case-insensitively.
3. The kiro-core engine shall treat a criterion without `_Guard:_` as applying unconditionally.
4. If a guard or effect does not conform to the grammar, including a comparison of a term with another term, the kiro-core engine shall record `GUARD_UNPARSED` of severity `error` at the annotation line naming the position and the reason, and shall exclude the criterion from the contradiction search.
5. If a guard or effect references a term that is not declared on the requirement or criterion, the kiro-core engine shall record `GUARD_TERM_UNDECLARED` of severity `error` at the annotation line naming the reference, and shall exclude the criterion from the contradiction search.
6. If a guard or effect uses a term whose resolved kind is `entity`, uses a bare reference for a term that is not `bool`, compares a `bool` term with a literal other than `true` or `false`, compares an `enum` term with a value outside its declared values or with an ordering operator, or compares an `int` term with a non-integer literal, the kiro-core engine shall record `GUARD_KIND_MISMATCH` of severity `error` at the annotation line naming the term, its kind and the offending literal or operator, and shall exclude the criterion from the contradiction search.
7. If a guard or effect references a declared term that did not resolve as found under Requirement 3, the kiro-core engine shall exclude the criterion from the contradiction search without recording a second finding for that term.
8. The kiro-core engine shall read an `_Effect:_` annotation on a criterion as a comma-separated list of assignments `term = literal` stating what the criterion requires, with the term and literal rules of 4.2 and 4.6 and equality as the only operator.
9. The kiro-core engine shall read a `_Conflicts:_` annotation on a criterion as a comma-separated list of criterion ids of the same requirements document whose responses are incompatible with this criterion's, shall treat the relation as symmetric, and, if an id names no criterion of the document, shall record `CONFLICT_REF_UNKNOWN` of severity `warning` at the annotation line naming the id.
10. The kiro-core engine shall treat two criteria as incompatible when either lists the other in `_Conflicts:_`, or when their effects assign different literals to the same term.

### Requirement 5: Bounded Contradiction Search
**Objective:** As a reviewer, I want to know whether two incompatible criteria can both apply in some state, with a concrete witness, or be told plainly that the search refused, so that "no contradiction" always means it was checked.

#### Acceptance Criteria
1. While the spec declares topics and the vocabulary is loaded, the kiro-core engine shall consider every pair of criteria of the feature that are incompatible under 4.10 and whose guards and effects were all accepted under Requirement 4, and shall consider no other pair; because every involved term resolved inside the spec's declared topics, no comparison crosses a topic the spec did not declare.
2. For each considered pair, the kiro-core engine shall decide exactly whether some assignment of values to the involved terms satisfies both guards, treating an unconditional criterion as satisfied by every assignment, each `bool` and `enum` term as holding exactly one of its values, and each `int` term as ranging over the regions delimited by the integer constants mentioned for that term in any guard or effect of the feature and by its declared bounds.
3. If both guards of a considered pair are jointly satisfiable, the kiro-core engine shall record `CONTRADICTION` of severity `error` at the line of the criterion that appears first in the document, naming both criterion ids, the reason (the declared conflict, or the term and the two effect values), and a witness assignment listing every term that occurs in either guard with its value, where an `int` value is given as the satisfying region.
4. When the guards of a considered pair cannot hold together, the kiro-core engine shall record no finding for the pair.
5. If a criterion's guard cannot hold under any assignment, the kiro-core engine shall record `GUARD_UNSATISFIABLE` of severity `warning` at its annotation line.
6. The kiro-core engine shall perform the search with a variable order fixed by the vocabulary (terms ordered by topic then id, each term's values contiguous) and no dynamic reordering, so that the same documents and vocabulary yield the same findings and the same witnesses on every run and target.
7. If the number of encoded values of the feature exceeds the configured variable cap, or the size of any intermediate decision structure exceeds the configured node cap, the kiro-core engine shall stop the search for the affected pairs and record `SEARCH_REFUSED` of severity `warning` on the requirements document naming the cap, the measured size, the affected pairs and the largest contributing terms, and shall never report a refused pair as free of contradiction.
8. The kiro-core engine shall bound the search by sizes only and never by elapsed time, so that the verdict for a given input does not depend on the machine.

### Requirement 6: Plugin Commands `check.*`
**Objective:** As a developer in OpenIDEA, I want to run the checks on the spec I am working on and read the findings in a notification, so that I fix criteria while writing them instead of at merge time.

#### Acceptance Criteria
1. The Kiro plugin shall provide the commands `check.spec`, `check.ears`, `check.terms` and `check.contradictions` as spec-addressable commands whose first argument token, when present, names the spec, and `check.spec` shall also be insert-capable.
2. When `check.spec` runs, the Kiro plugin shall run all three checks for the resolved spec with pattern reports disabled and term suggestions enabled, and shall show one notification whose title names the spec and the counts of errors, warnings and info findings, whose level derives from the finding severities, and whose text contains one summary line per check (ran with its finding count, or skipped with its reason) followed by the findings in the shared findings text form; when the insert flag is set the complete text shall also be inserted at the cursor.
3. When `check.ears` runs, the Kiro plugin shall run only the EARS check with pattern reports enabled and shall show the number of criteria per pattern before the findings.
4. When `check.terms` runs, the Kiro plugin shall run only the term check and shall show a scope line (spec, declared topics, vocabulary status) and the counts of declared terms that resolved, were deprecated, mismatched, undeclared, ambiguous and suggested before the findings.
5. When `check.contradictions` runs, the Kiro plugin shall run only the contradiction check and shall show the number of criteria with guards, the pairs considered, the contradictions found, the pairs refused and the caps in use before the findings.
6. When a check produces no finding, the Kiro plugin shall state that explicitly in the notification rather than showing an empty body.
7. While the spec declares no topics or the vocabulary is missing or invalid, `check.terms`, `check.contradictions` and `check.spec` shall complete successfully with the explanatory finding of 3.8 and a pointer to the vocabulary documentation and `vocab.topics`.
8. The Kiro plugin shall register `check.spec`, `check.spec.insert`, `check.ears`, `check.terms` and `check.contradictions` statically with titles starting with `Kiro:` and shall gain per-spec variants of the four base commands through plugin-core's variant mechanism.
9. If the current spec cannot be resolved, the Kiro plugin shall return plugin-core's unresolved-spec error unchanged, and the Kiro plugin shall read the vocabulary file at most once per command and shall never write any file.

### Requirement 7: Annotation Convention Documentation
**Objective:** As a spec author adopting the conventions, I want the annotations documented with examples and the template change proposed, so that teams can opt in deliberately.

#### Acceptance Criteria
1. The checks documentation shall describe the `_Terms:_`, `_Guard:_`, `_Effect:_` and `_Conflicts:_` annotations with their placement (requirement block or indented under a criterion), the guard grammar of 4.1, the term-reference rule of 4.2, the allowed kinds and literal forms per kind, the integer region rule of 5.2, and one worked example that produces a contradiction with its witness.
2. The checks documentation shall list every finding code of this spec with its default severity and meaning, and shall explain that `SEARCH_REFUSED` means the pairs were not checked and which levers narrow the search.
3. The checks documentation shall state that a document without annotations produces no term or contradiction failure, and shall propose the change to the cc-sdd requirements template (commented annotation hints under a requirement and under a criterion) without applying it to the templates or skills.
4. The checks documentation shall state that the contradiction search considers only pairs whose terms resolved inside the spec's declared topics, so that cross-topic contradictions are a documented blind spot, and shall present `CHECK_COVERAGE` as the signal that distinguishes "checked, nothing found" from "not checked".

### Requirement 8: Engineering Quality
**Objective:** As a maintainer, I want the checks to meet the engine's and plugin's standards, so that they run identically in the sandbox and in CI and never take the plugin down.

#### Acceptance Criteria
1. The kiro-core engine shall accept any requirements text, annotation value and guard text without panicking, returning findings instead of errors, and shall build for both the native and the sandbox target.
2. The kiro-core engine shall produce byte-identical check reports for the same documents, vocabulary and configuration across runs and targets.
3. The kiro-core engine shall register every finding code of this spec in its finding catalogue with the stated default severity and a description, so that the catalogue test and the crate documentation stay complete.
4. The kiro-core engine shall complete the EARS and term checks over a requirements document of 1000 criteria in under one second in a native release build, and shall complete the contradiction search over a generated document of 200 guarded criteria over 32 declared terms (enum terms with up to 8 values, int terms split at up to 8 constants) within the default caps in under one second in a native release build.
5. The repository shall contain fixtures with a known-good requirements document (no warning or error finding, and no informational finding other than `CHECK_COVERAGE` under the default configuration), a known-bad document (every finding code of this spec at least once, except the refusal), a refused document (default caps exceeded), and the EARS regression cases of 2.10, each stating the findings it is expected to produce.
6. The kiro-core engine shall provide tests over the fixtures covering every finding code, every EARS pattern, every term outcome, the witness content, determinism across two runs, and the no-annotation guarantee of 1.6 over this repository's own existing specs.
7. The Kiro plugin shall provide native end-to-end tests that run the four `check.*` commands against a simulated host with a fixture project, covering findings present, no findings, no topics, missing vocabulary, invalid vocabulary, the insert flag and the unresolved-spec error, and a manifest consistency check that includes the check commands.
