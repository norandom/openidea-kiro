# Requirements Document

## Project Description (Input)

**Who has the problem.** Teams running kiro / cc-sdd with coding agents writing most of the code, and the humans who review it: the spec workflow gates requirements, design and tasks, but nothing gates the code the tasks produce. The maintainer of this repository is the first such team.

**Current situation.** Over a sequence of agent-implemented tasks the code base degrades in ways no task review catches: routines grow past what a reader can hold, one file accretes everything a spec touches, the same routine is written again under another name, a constant or a set of state literals is copied into many files, and data code addresses columns by position. Each piece passes review on its own. `../scitools-hook` solves this for SciTools Understand users with a commit-time gate (per-entity limits, a never-worse-than-before ratchet, lexical duplication rules, a scattered-definitions rule, hints with edit tags, a rules block in the agent's instructions), but it is licence-bound and knows nothing about specs. This project has the file ↔ component ↔ task join, a finding shape, a CLI gate and a vocabulary, and none of it reads source code.

**What should change.** A code gate inside the kiro workflow: the complexity gate, the anti-god-file and anti-god-type limits, scitools-hook's lexical similarity (duplicate blocks and similar-routine families), scattered definitions, the new scattered-state and role-named data access rules; a ratchet so only regression blocks; every finding attributed to the owning spec, component and tasks; selection per task so an implementer gates one task before marking it complete; the effective rules written into steering for the agent; honest coverage reporting; this repository gating itself.

## Introduction

code-constraints (below: the Code Gate) extends spec constraint checking from the specification to the implementation. Where spec-constraints asks whether a requirement is well-formed, grounded and consistent, the Code Gate asks whether the code a task produced is still something a reader — human or agent — can hold: small enough routines, files and types; no second copy of a routine the project already has; no decision copied into a dozen files; data addressed by role, not by position. It judges only what it measured, blocks only regression, and says what it did not measure.

The Code Gate is delivered as a `code` command family of `kiro-cli` (`code check`, `code baseline`, `code rules`, `code config`) over three kinds of input: source files it measures natively (Rust, Python, TypeScript/JavaScript bundled), analyzer reports a team already produces (scitools-hook JSON as the full-fidelity licensed source, jscpd JSON for duplicates in other languages), and the project's own specs, whose design File Structure Plans attribute every finding to a spec, a component and the tasks bound to it. Rules, defaults, exceptions and their written reasons live in one committed file, `.kiro/code-rules.toml`; the before side of the ratchet lives in a committed baseline, `.kiro/code-baseline.json`, or in a git revision named on the command line; the effective rules are written into `.kiro/steering/code-rules.md` so the agent reads them before writing code. Findings use the project's one finding shape and codes (`CODE_*`), the same text and JSON forms and the same exit codes as `kiro-cli check`.

The rule catalogue, its defaults and its documented blind spots are taken from `../scitools-hook` where the measurement transfers (`research.md` holds the feature map and the pendant-or-custom decision per feature); the scattered-state and role-named data access rules are new, and the latter is the return of the roadmap's deferred "idiomatic naming in data code" as a vocabulary-grounded rule.

Three amendments (2026-11-09) extend the approved requirements: a breadth ledger in the shape of `../QOpenBB`'s `.kiro/breadth.toml` linking capabilities to criteria, tests and evidence, checked by `breadth check` (the return of the roadmap's deferred "requirement → test traceability"); an end-to-end suite over the real binary as the primary acceptance of every capability; and a shared command-line parameter library that every command of `kiro-cli` composes.

## Requirements

### Requirement 1: Measurement Sources
**Objective:** As an operator, I want the Code Gate to measure code natively where it can and to accept reports from analyzers I already run, so that one gate covers the project's languages without a second configuration per tool.

#### Acceptance Criteria
1. The Code Gate shall measure, natively and without any external tool, the routine, type and file facts of Requirements 3 and 4, the token facts of Requirement 5, the module-level bindings of Requirement 6, the literal comparisons of Requirement 7 and the data access patterns of Requirement 8 for Rust, Python and TypeScript/JavaScript source files, documenting the bundled languages and the file extensions it maps to each.
2. The Code Gate shall accept one or more report files produced by scitools-hook (`--format json`) and by jscpd (JSON reporter) as measurement sources named on the command line or in the configuration, mapping every imported record to the Code Gate's finding shape with the originating tool and rule named in the message, and documenting for each accepted format which facts it supplies and which it cannot.
3. The Code Gate shall treat a value a source supplies for an entity as a measurement eligible for limits and the ratchet, and a breach a source supplies without a value as an imported finding that carries no before value and says it is not ratcheted.
4. If a report file cannot be read, is not valid JSON or does not match its declared format, the Code Gate shall report `CODE_SOURCE_INVALID` as an error naming the file and the first problem, continue with every other source, and count the failure in the coverage finding of Requirement 11.
5. When the same entity is measured both natively and by a report source, the Code Gate shall use the native measurement for limits and the ratchet, reporting a differing value once per run at info level with both sources and values.
6. While a selected file is in a language no source covers, the Code Gate shall list it as not measured in the coverage finding and produce no finding about its content.
7. Where a source is marked `required` in the configuration and its report is absent or invalid, the Code Gate shall stop with an error naming the source and exit with code 2, so that a pipeline cannot pass by forgetting to run the analyzer.

### Requirement 2: Configuration, Defaults and Reasons
**Objective:** As a project maintainer, I want the limits, rule switches and exceptions in one committed file with measured defaults, so that the gate's judgement is reviewable and no agent can relax it silently.

#### Acceptance Criteria
1. The Code Gate shall read its configuration from `.kiro/code-rules.toml` under the project root, running with the built-in defaults when the file is absent.
2. The Code Gate shall ship every default limit and severity of Requirements 3 to 9 as documented in the rules reference together with the measurement or source that justified it, with no blocking default for a rule or metric without a recorded measurement: such a rule ships as a warning or off.
3. The Code Gate shall accept, per rule and per metric, a severity (`error`, `warning`, `info`, `off`) and a limit, name and path ignore lists where a rule defines them, and path scopes that override routine, type and file limits for the files they match, with the most specific matching scope winning and documented tie rules.
4. The Code Gate shall require a `reason` text on every scope, on every ignore entry and on every limit or severity looser than the shipped default, rejecting a configuration lacking one with `CODE_CONFIG_INVALID` naming the key and exit code 2 before measuring anything.
5. If the configuration names an unknown rule, metric, severity or key, a limit that is not a number, or a required source the Code Gate does not know, the Code Gate shall stop with `CODE_CONFIG_INVALID` naming the entry and exit with code 2.
6. When `code config` runs, the Code Gate shall print every effective limit, severity, scope, ignore entry and source with where it came from (default, file or scope) and its reason, so that what the gate enforces is inspectable without reading the file.

### Requirement 3: Routine Complexity and Size Limits
**Objective:** As a reviewer of agent-written code, I want every routine judged against complexity and size limits, so that a routine stays something a reader reasons about rather than approximates.

#### Acceptance Criteria
1. The Code Gate shall measure for every function and method its strict cyclomatic complexity (one plus every decision point, counting each `&&` and `||` operand), its deepest nesting depth, its lines containing code, its statements and its declared parameters, judging them against the defaults cyclomatic 10, nesting 3, code lines 60, statements 40 and parameters 5, each as an error.
2. The Code Gate shall measure the lines per statement for routines of at least 5 statements and the comment lines of every routine, judging them against the defaults 4 and 20 as warnings, so that length without complexity is reported without blocking.
3. When a measured value exceeds its limit, the Code Gate shall report `CODE_ROUTINE_LIMIT` naming the routine, the metric, the value, the limit and the scope the limit came from, with a `simplify:` hint naming the remedy for that metric (guard clauses or extraction for complexity and nesting, extraction for length, an options record for parameters, fewer lines per statement or fewer comment lines for the shrink metrics).
4. The Code Gate shall judge every limit strictly, treating a value equal to its limit as passing.
5. Where a source supplies cognitive complexity, essential complexity or path count for a routine, the Code Gate shall accept a configured limit on it and judge it as any other routine metric, with the documentation stating that the native measurer does not compute these three.
6. When `--show-highest` is given, the Code Gate shall print for every routine, type and file metric the highest measured value and where it stands, so that the first run on a grown repository reads as a distribution and not as a verdict.

### Requirement 4: Container Limits
**Objective:** As a reviewer, I want files and types judged by how much they hold, so that a module that accretes everything is refused before it becomes the place every change touches.

#### Acceptance Criteria
1. The Code Gate shall measure for every file its lines containing code, its declared functions, its declared types (classes, structs, enums, traits, interfaces, type aliases excluded) and the highest routine cyclomatic complexity inside it, judging them against the defaults code lines 500 and declared functions 25 as errors, highest cyclomatic 10 as an error, and declared types 8 as a warning until a measurement on a Rust and a TypeScript tree is recorded.
2. The Code Gate shall measure for every type its declared methods and its declared fields or attributes, counting for Rust the methods of every inherent implementation block of the type in the same file, and judging them against the defaults methods 20 and fields 10 as errors.
3. When a file or type exceeds a limit, the Code Gate shall report `CODE_FILE_LIMIT` or `CODE_TYPE_LIMIT` naming the container, the metric, the value and the limit, with a `split:` hint that names a cohesive group to move and, when the file is owned by a spec, the design component so the split is made in the File Structure Plan first.
4. The Code Gate shall never apply the ratchet of Requirement 9 to the container counts (file code lines, declared functions, declared types; type methods, fields), so that splitting a container is never refused for raising a neighbour's count, while the absolute limits of this requirement still apply.
5. The Code Gate shall accept coupling, cohesion and inheritance depth of types from a report source as any other type metric, with the documentation stating that they are not measured natively because they need name resolution.

### Requirement 5: Duplicate Blocks and Similar-Routine Families
**Objective:** As a reviewer, I want a copy or a renamed copy of code the project already holds reported as one finding naming the original, so that an agent that writes the same routine again is told where it already exists.

#### Acceptance Criteria
1. The Code Gate shall report `CODE_DUPLICATE_BLOCK` for a run of at least 12 consecutive code lines in a selected file that the project holds at another location, where a code line is the file's lexemes with whitespace and comments removed and each line is compared by hash, naming up to three other locations; two copies in one file count, both ends are reported when both are selected, and a run that repeats only itself is not reported.
2. The Code Gate shall compute for every routine of at least 6 statements a token shape in which every identifier becomes one token kind and every literal one token kind, scoring two shapes by two times the matched length over the sum of their lengths and grouping routines whose pairwise score reaches 0.9 into families of at least 2 members.
3. When a family contains a selected routine, the Code Gate shall report one `CODE_SIMILAR_FAMILY` finding for the family naming the other members with their locations, the family size and the weakest similarity holding it together, with a `shrink:` hint when every member is in one file and a `delete:` hint when the family spans files.
4. The Code Gate shall exclude from families a routine nested inside its container's shape, routines whose names match the shipped name ignore list (dunder methods, test setup and teardown hooks) or the configured one (neither reported, nor named, nor a link between two families), pairs of different languages, and routines whose statement count could not be taken.
5. The Code Gate shall refuse a pair before scoring it when the length band or the token multiset makes the threshold unreachable, so that the pass is exact and no family is lost, with both bounds documented as exact ceilings rather than approximations.
6. The Code Gate shall document that the family rule finds a routine that was copied and renamed and does not find a routine that was re-implemented in another shape (the scitools-hook measurement: 1.00 for a rename, 0.64 for guard clauses rewritten as a ladder, 0.34 for a table-driven rewrite), and that an embedding-based clone finder is a periodic report a human or an agent reads and is never a reason a change is refused.
7. When a jscpd report is a source, the Code Gate shall import each clone as `CODE_DUPLICATE_BLOCK` naming the tool, without reporting a line range twice when the native rule also found it.

### Requirement 6: Scattered Definitions
**Objective:** As a maintainer, I want a constant that was copied instead of shared reported, so that changing a policy does not mean finding every file that hardcodes it.

#### Acceptance Criteria
1. The Code Gate shall collect every module-level binding of the project (constants, statics and module-scope assignments) with its name and the text of its initialiser, skipping a binding whose initialiser does not close within 12 lines or cannot be read, so that unreadable initialisers are never grouped.
2. When a name is bound to the same initialiser text in more files than `max_files` (default 3), the Code Gate shall report `CODE_SCATTERED_DEFINITION` against each such file in the selection naming the binding, its text and up to three other files, with a `collect:` hint (declare it once and import it; when the copies are not one decision, add the name to the ignore list with a reason).
3. The Code Gate shall key on the name and the value together, so that a name bound to a different value in each file is not reported.
4. The Code Gate shall accept an ignore list of binding names for the per-module idiom, shipped with the documented names that are written out in every module on purpose (`log`, `logger`, `pytestmark`, `__all__`) and documented as a list of names rather than values.
5. When one name is bound to two or more different values and each value stands in at least `max_files` files, the Code Gate shall report the groups separately and add one info finding naming the name and its values, so that one name with two meanings stays visible instead of being unified by accident.
6. The Code Gate shall document that comparison is textual, that a value referencing another module-level name can over-report, and that semantic equality is not inferred.

### Requirement 7: Scattered State
**Objective:** As a reviewer, I want a set of states that is tested in many files reported as one finding, so that a state machine spread across the code base gets one owner and one transition table.

#### Acceptance Criteria
1. The Code Gate shall collect, project-wide, every comparison of a subject against a string or integer literal (equality and inequality tests, match arms over literals, membership tests over literal collections), grouped by the subject's name as written (a variable, field or accessor such as `status`, `self.state`, `job.phase`) and the set of literal values it is compared with.
2. When a subject is compared with at least `min_states` (default 2) distinct literal values and those comparisons stand in more files than `max_files` (default 3), the Code Gate shall report `CODE_SCATTERED_STATE` against each such file in the selection naming the subject, the values, the number of files and up to three other files, with a `collect:` hint (one enumeration type and one owner — a transition function or table — so comparisons become calls or exhaustive matches).
3. Where the language has enumeration types, when the same enumeration is matched over all its variants in more files than `max_files`, the Code Gate shall report `CODE_SCATTERED_STATE` at info level naming the enumeration and the files, so that a transition-table candidate is visible without being refused.
4. The Code Gate shall report each subject at most once per file, never for a subject whose comparisons all stand in one file and never for a subject on the configured ignore list of subject names with reasons.
5. The Code Gate shall document what the rule cannot see: a state carried in booleans, a state tested through a helper predicate, two unrelated subjects that share a name, and literal values compared through a variable.

### Requirement 8: Role-Named Data Access
**Objective:** As a reviewer of data code, I want columns, fields and axes of arrays and dataframes addressed by a role name grounded in the project vocabulary rather than by position, so that a reader knows what a column means without the notebook that produced it.

#### Acceptance Criteria
1. The Code Gate shall report `CODE_POSITIONAL_ACCESS` as a warning when a tabular receiver is indexed by an integer literal in a column, field or axis position according to the shipped per-language patterns (for Python: dataframe positional column selection, the column axis of a two-dimensional array, element access on a row record; for Rust: positional column selection on dataframes, the column axis of two-dimensional arrays), with a `name:` hint (select the column by its role name, or give the row a typed record).
2. Where the configuration names one or more vocabulary topics as data topics, the Code Gate shall resolve every column or field name used in data code (string literals and attribute names in column-selection positions, field names of row records) against those topics through the vocabulary's scoped resolution, reporting `CODE_COLUMN_UNGROUNDED` as a warning for a name that resolves to no term with the nearest terms as suggestions.
3. While no data topic is configured, the Code Gate shall run only the positional check, stating in the coverage finding that column names were not grounded so that a data file is never reported clean without saying so.
4. When the same column-name literal is used in more files than `max_files`, the Code Gate shall report `CODE_SCATTERED_SCHEMA` at info level against each such file naming the literal and the files, with a `collect:` hint (one schema or constants module, or a typed row record, owned by one design component).
5. The Code Gate shall ship the receiver and position patterns for Python (pandas, polars, NumPy) and Rust (polars, ndarray), documented, and accept additional patterns per language from the configuration with a reason.
6. The Code Gate shall document what the rule cannot see: a position computed from a variable, a name built at runtime, access through a helper, and receivers the patterns do not name.

### Requirement 9: Ratchet, Baseline and Net Growth
**Objective:** As an operator adopting the gate on a grown code base, I want only regression to block, so that the gate can be installed today and the trend becomes monotonic without a cleanup project.

#### Acceptance Criteria
1. The Code Gate shall identify every measured entity by a key that is stable across two measurements — scope, project-relative path, qualified name and parameter list — so that an entity is compared with itself on the before and the after side.
2. When a before side exists and an entity's value moved in the worse direction, the Code Gate shall report `CODE_RATCHET` naming the entity, the metric, the before and after values and the limit: as an error when the after value exceeds the limit, and as a warning when it is still within the limit.
3. When a before side exists and an entity exceeds a limit on both sides without worsening, the Code Gate shall mark the limit finding as pre-existing, report it, and never let it block unless the configuration's strict mode is on.
4. The Code Gate shall take the before side from the committed baseline file `.kiro/code-baseline.json` when it exists, or from the git revision named by `--changed <rev>` when given (the named revision wins when both exist), saying in the output which one was used and reporting no ratchet finding and no pre-existing status when neither exists.
5. The Code Gate shall never apply the ratchet to the container counts of Requirement 4 or to imported breach-only findings, with the rules reference saying so.
6. When an entity exists only on the after side, the Code Gate shall judge it by the absolute limits alone, except that exactly one key disappearing and exactly one appearing with the same scope, path and qualified name is paired as a signature change and ratcheted across the pair.
7. When a before side exists, the Code Gate shall print one net line for the run — statements added minus removed with the sign always written, lines beside it, over the number of routines counted — reporting `CODE_NET_GROWTH` only where the configuration sets a maximum net growth.
8. When `code baseline` runs, the Code Gate shall write the baseline deterministically (sorted keys, no timestamps, the effective configuration digest recorded) so that two captures of the same tree are byte-identical.
9. When a run finds that the baseline's recorded configuration digest differs from the effective configuration, the Code Gate shall report `CODE_BASELINE_STALE` at info level naming both.

### Requirement 10: Spec Ownership and Task Selection
**Objective:** As a developer in a spec-driven project, I want every code finding attributed to the spec, component and tasks that own the file, so that degradation is read in the language of the specs and the fix lands in the right task.

#### Acceptance Criteria
1. When a finding concerns a file that a discovered spec's design File Structure Plan maps to a component, the Code Gate shall set the finding's feature to that spec and name the component and the tasks whose boundary names it in the finding, using the engine's ownership join and never re-deriving the mapping.
2. When a file is mapped by more than one spec, the Code Gate shall set the feature to the first spec in roadmap order (discovery order when the roadmap lists none) and name the others in the finding.
3. When a selected file with at least one finding is mapped by no spec, the Code Gate shall report `CODE_FILE_UNOWNED` at info level once per file per run, so that code outside every spec is visible.
4. When `--spec <name>` is given, the Code Gate shall judge only the files that spec's design maps, and when `--task <spec>:<id>` is given only the files of the components the task's boundary names, failing with exit code 2 and the available specs, tasks or components when the spec, the task or the boundary is unknown or the task has no boundary.
5. The Code Gate shall print a per-spec summary in the text and JSON reports — findings by severity, files measured, and the net line where a before side exists — ordered by roadmap order then name, with unowned files summarised last.
6. The Code Gate shall accept `--files <path>...` and `--all` as selections in the same way as `--spec` and `--task`, so that a pre-commit hook or a pipeline can select by path or by whole tree.

### Requirement 11: Trust Signals and Degradation
**Objective:** As a reviewer, I want to know what the gate did not measure, so that a clean report is never mistaken for a checked one.

#### Acceptance Criteria
1. Whenever a run completes, the Code Gate shall record `CODE_COVERAGE` at info level stating the files selected, the files measured natively, the files measured through each report source, the files not measured by language, the rules that ran, the rules skipped with their reasons, whether column names were grounded and against which topics, and whether a before side was used and which.
2. If a selected source file cannot be parsed into a syntax tree or contains an error node, the Code Gate shall report `CODE_PARSE_FAILED` as an error naming the first error position and stating that the file cannot be reported as checked, judging no rule on that file.
3. If a file outside the selection fails to parse, the Code Gate shall report it at warning level without blocking.
4. When a rule is off or cannot run (no source supplies its facts, the language is not covered), the Code Gate shall report it as skipped in `CODE_COVERAGE` and produce none of its findings.
5. The Code Gate shall filter nothing silently: warnings, info and pre-existing findings are printed and counted, and only findings at or above `--fail-on` that are not pre-existing decide the exit code.
6. The Code Gate shall document per rule what it deliberately does not report, stating in the rules reference and in the steering block that whether the standard library, the platform or an installed dependency would have replaced a piece of code is never checked, so that their absence from a report is not a clearance.

### Requirement 12: Agent Feedback Contract
**Objective:** As the operator of an agent harness, I want the limits in the agent's context before it writes code, every finding to carry an edit it can make, and the gate to be unrelaxable by the agent, so that agents follow the rules instead of learning them from refused commits.

#### Acceptance Criteria
1. When `code rules --write` runs, the Code Gate shall write the effective rules as a block into `.kiro/steering/code-rules.md` between a begin and an end marker, replacing a previous block and preserving the rest of the file, generated from the effective configuration so that it cannot drift, and listing the limits per scope, the rules in force with their hint tags, the lean ladder with the rungs that are the agent's alone, the ratchet statement and the per-task self-check command.
2. The Code Gate shall open every finding's hint with exactly one tag from `simplify:`, `split:`, `delete:`, `shrink:`, `collect:`, `name:` and `fix:` (the last reserved for findings about the run itself: parse failures, invalid sources or configuration, a stale baseline, coverage), followed by what to change and what replaces it in one line, carrying the hint and the tag as separate fields in the JSON report.
3. The Code Gate shall provide a JSON report in which every finding carries severity, code, feature, file, line, message, hint, tag, metric, value, before value, limit, limit source, pre-existing flag, entity key and owning component and tasks, under a schema version, with no timestamps and a deterministic order, so that a harness can inject it into an agent's context and two runs over the same input are byte-identical.
4. The `kiro-impl` and `kiro-review` skills shall instruct the agent to run the task-scoped code check before marking a task complete and to resolve every blocking finding by changing code — never by editing `.kiro/code-rules.toml`, the baseline or an ignore list.
5. The `kiro-validate-impl` skill shall include the whole-tree code check against the baseline as a validation gate.
6. The Code Gate shall document a human-owned adaptation procedure in which a limit is loosened, a scope added or a finding ignored only through a configuration change carrying a reason, reviewed by a human, followed by regenerating the steering block, with the `agent-guidance` steering naming the Code Gate as the code half of the feedback contract.

### Requirement 13: Command Line, Exit Codes, Determinism and Performance
**Objective:** As a CI maintainer, I want the code gate run by one command with the exit-code contract of the spec gate, so that a pipeline blocks on code degradation exactly as it blocks on spec findings.

#### Acceptance Criteria
1. The kiro-cli shall offer `code check` with the selections `--all`, `--changed <rev>`, `--spec <name>`, `--task <spec>:<id>` and `--files <path>...`, the options `--format text|json`, `--fail-on error|warning`, `--show-highest` and `--source <format>=<file>` (repeatable), and the companions `code baseline`, `code rules [--write]` and `code config`.
2. The kiro-cli shall exit with code 0 when no finding at or above `--fail-on` remains after pre-existing findings are excluded, 1 when at least one does, and 2 on a usage, configuration, filesystem or required-source failure, printing one line on standard error for the last.
3. Where `--sarif <path>` is given, the Code Gate shall write the findings as a SARIF 2.1.0 document to that path beside the chosen report, with the rule identifiers equal to the finding codes and the hint carried as the result message's remediation text.
4. The Code Gate shall produce byte-identical text and JSON reports for the same tree, configuration and sources across runs and platforms: project-relative paths with `/` separators, newline-only line endings, no absolute paths, no timestamps, findings sorted by the engine's order.
5. The Code Gate shall complete `code check --task` over any task of this repository within 10 seconds and `code check --all` over this repository within 60 seconds in a release build on the development machine, with both figures measured and recorded in the research log and held by release-only tests.
6. While running any command, the Code Gate shall read source files only under the project root and report files named explicitly as given, writing nothing except the baseline file on `code baseline`, the steering file on `code rules --write` and the `--sarif` path when asked.

### Requirement 14: Self-Application, Fixtures, Documentation and Tests
**Objective:** As a maintainer of this repository, I want the gate to pass on its own code and to be documented with fixtures, so that the rules are credible and the measurements behind the defaults are recorded.

#### Acceptance Criteria
1. The repository shall gate itself: the CI workflow runs `kiro-cli code check --all --fail-on error` against a committed baseline through a `cargo kiro-code` alias, and the first inventory of this repository (findings by rule and the highest values) is recorded in the research log with the note that the first number is not a quality score.
2. The repository shall contain fixtures with a known-clean tree and one tree per rule producing exactly that rule's findings — routine limits, container limits, duplicate block, similar family including the nested-twin exclusion and the name ignore, scattered definition including the idiom ignore and the one-name-two-values case, scattered state including the single-owner case, positional access and an ungrounded column against a vocabulary with a data topic, ratchet with a before and after pair including a signature change, an unowned file, a parse failure, an invalid report source — each stating the findings it is expected to produce.
3. ## Amendments (2026-11-09, after requirements approval)

Three additions requested by the owner before task approval. They extend the approved requirements; they do not change them.

### Amendment A1: Breadth ledger workflow (extends Requirement 12 / Requirement 14)
**Objective:** As an owner reviewing what has actually been verified, I want a committed ledger linking each capability to its requirement criteria, its tests and its evidence, in the shape of QOpenBB's `.kiro/breadth.toml`, so that "planned" is never mistaken for "passed" and every spec's criteria are visibly mapped or visibly unmapped.

#### Acceptance Criteria
1. The repository shall keep a committed ledger `.kiro/breadth.toml` of `[[capabilities]]` entries, each with an `id`, `requirements` (references of the form `<spec>:<criterion>` with single criteria, whole requirements or ranges within one requirement, the QOpenBB path form `<spec>/requirements.md:<ref>` also accepted), `planned_checks`, `test_paths`, `e2e_paths`, a `status` from `planned`, `implemented`, `partial`, `unverified`, `passed`, `deferred`, and `evidence` records.
2. When `breadth check` runs, the kiro-cli shall resolve every requirement reference against the discovered specs' criteria and report `BREADTH_REQ_UNKNOWN` as an error for a reference naming no spec, requirement or criterion.
3. When `breadth check` runs, the kiro-cli shall verify that every listed test and end-to-end path exists under the project root (a `path::name` form names the file before `::`), reporting `BREADTH_TEST_MISSING` as an error, or as a warning while the capability's status is `planned`.
4. The Code Gate shall report `BREADTH_STATUS_UNSUPPORTED` as an error when a status claims more than its entry supports: `passed` without at least one test path, one end-to-end path and one evidence record; `implemented` without a test path; `partial`, `unverified` or `deferred` without an evidence record stating what is missing or why.
5. When every task that references a capability's criteria is complete in its spec's tasks document while the capability's status is still `planned`, the kiro-cli shall report `BREADTH_STALE` as a warning naming the capability and the spec, so that planned checks are never read as completed tests.
6. When `breadth check` runs, the kiro-cli shall report `BREADTH_CRITERION_UNMAPPED` at info level once per spec whose tasks have been generated, naming the number and the first five criteria that no capability maps, and `BREADTH_COVERAGE` at info level summarising capabilities by status and mapped criteria per spec.
7. If the ledger is absent, is not valid TOML, lacks the capabilities list, repeats an id or uses an unknown status, the kiro-cli shall report `BREADTH_INVALID` as an error with the line of the first problem and evaluate nothing else from the file.
8. The `kiro-impl`, `kiro-validate-impl` and `kiro-spec-tasks` skills shall carry the ledger workflow: a spec's capabilities are entered as `planned` when its tasks are generated, a task's completion moves the mapped capability to `implemented` with its actual test paths, and validation moves it to `passed` only with the end-to-end path and a dated evidence record naming the command, the revision and the result.
9. The repository shall seed the ledger with this spec's own capabilities as `planned` at task generation, reaching `passed` for them only through the end-to-end suite of Amendment A2, with `breadth check` run in the CI gate.

### Amendment A2: End-to-end acceptance first (extends Requirement 14)
**Objective:** As the owner, I want every user-visible capability of the Code Gate accepted by an end-to-end journey over the real binary and a real repository, so that unit coverage supports but never substitutes for behaviour a user would observe.

#### Acceptance Criteria
1. The repository shall provide an end-to-end suite that drives the built `kiro-cli` binary over temporary projects assembled from real spec trees, source trees and, where a journey needs history, real git repositories created by the test, asserting on standard output, standard error, exit codes and written files rather than on internal types.
2. The end-to-end suite shall cover at least these journeys: the implementer loop (a task-scoped check blocks, the code is fixed, the same check passes); the CI loop (baseline captured, a routine regresses, the whole-tree check exits 1 with a ratchet finding, pre-existing debt alone exits 0); the change loop (`--changed <rev>` over a two-commit repository with a worsened and a new routine, net line printed); the onboarding loop (`code config`, `code rules --write`, the steering block present, spec gate and code gate both run); the sources loop (scitools-hook and jscpd reports imported, a required source missing exits 2); the breadth loop (a ledger moving from `planned` to `implemented` to `passed`, each wrong claim refused); the attribution loop (a finding names its spec, component and tasks; an unowned file is reported).
3. The end-to-end suite shall record for every journey the command line, the exit code and a digest of standard output in the test's own output, so that a failing journey can be reproduced from the log alone.
4. The CI gate shall run the end-to-end suite after the unit and integration suites, with a capability of this spec marked `passed` in the breadth ledger only when it carries an end-to-end path from this suite.
5. The repository shall keep the end-to-end suite runnable on the development machine and in the Dagger container with the same commands, with any journey that needs a tool the container lacks skipped with a visible message naming the tool, never silently.
6. The rules reference shall state the end-to-end-first policy: a capability's acceptance is its journey, unit tests pin algorithms, and a clean unit run is not acceptance.

### Amendment A3: Common command-line parameter standard as a library (extends Requirement 13)
**Objective:** As a user of the project's command lines, I want every command to accept the same global, output and gate parameters with the same names, defaults, environment fallbacks and exit codes, provided by one shared library, so that learning one command teaches the rest and a second binary inherits the standard.

#### Acceptance Criteria
1. The repository shall provide a library crate that defines the shared parameter groups — global (project root with its alias, verbosity as `-v`/`--verbose` and `-q`/`--quiet`, colour choice), output (`--format text|json`, `--output <path>` with `-` for standard output), gate (`--fail-on error|warning`) — together with the exit model (`0` clean, `1` findings at or above the gate, `2` usage, configuration or I/O failure) and the one-line failure form, for any binary in this workspace to compose.
2. The kiro-cli shall compose every command — the existing `check`, `status`, `graph`, `tasks`, `vocab validate`, `vocab import` and the new `code` and `breadth` families — from the shared groups, keeping every flag accepted today as an alias (`--root` for `--project`, `--table` for `--format table` on `graph` and `tasks`, `--out` for `--output` on `vocab import`) so that no existing invocation breaks.
3. The kiro-cli shall take each shared parameter from, in order, the command line, an environment variable (`KIRO_PROJECT`, `KIRO_FORMAT`, `KIRO_FAIL_ON`, `NO_COLOR` and `CLICOLOR_FORCE` for colour), then the built-in default, documenting the precedence.
4. The kiro-cli shall follow one naming rule for every parameter: long flags in kebab-case, short flags only for verbosity, quiet, help and version, repeatable flags written once per value, enumerated values in lowercase, and paths printed project-relative with `/` separators.
5. The kiro-cli shall write a machine-readable document to standard output only, with `schema_version` as its first key, and every diagnostic to standard error, for every command that offers `--format json`.
6. The kiro-cli shall offer `completions <shell>` printing a shell completion script generated from the command definitions, and `--version`.
7. The repository shall provide a conformance test that walks every command and subcommand of the binary and asserts the shared groups are present with identical names, values and defaults and that no short flag outside the allowed set exists, and a command-line standard document that the test keeps in agreement with the binary's help output.
